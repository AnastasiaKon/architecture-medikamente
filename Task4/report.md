# Task 4. Оценка узких мест при миграции

Диаграмма Исикавы: `ishikawa-migration.drawio` (превью `ishikawa-migration.png`).

## 1. Ситуация

Мигрируется монолитный ландшафт «Медикаменте» (Excel и сканы на общем
диске, файловые базы 1С, один физический сервер со всеми ролями) на
платформу из доменных сервисов в Kubernetes с API Gateway, Keycloak,
PostgreSQL/S3, Airflow и ClickHouse (см. Task2). Миграция идёт на фоне
открытия филиалов, пятикратного роста данных и массового найма.

Затрагиваемые процессы и компоненты:

| Область | Что затрагивается |
|---|---|
| Базы данных | Excel/сканы -> PostgreSQL + S3; файловые базы 1С -> клиент-серверный режим; появление ClickHouse |
| Каналы связи | ЛВС без сегментации -> VLAN, mTLS; OLE -> HTTP-сервисы; почта -> API с лабораторией |
| Серверное оборудование | один сервер в офисе -> кластер K8s в ЦОД; параллельная работа старого и нового |
| Бизнес-логика | журналы, запись, медкарта, оплата переносятся в сервисы; появляются согласия, RBAC/ABAC, шифрование полей |
| Люди и процессы | 3 ИТ-специалиста; ресепшен, врачи и кассиры переходят на порталы; новые регламенты |

## 2. Категории причин и возможные проблемы (по диаграмме)

### Инфраструктура
- Один физический сервер - нет ресурсов на параллельную работу старой и новой систем в период миграции.
- Сеть без сегментации: ETL, репликация и бэкапы конкурируют с трафиком ККМ и рабочих мест.
- Нет опыта эксплуатации K8s под нагрузкой: не настроены лимиты, autoscaling, PodDisruptionBudget.
- Хранилище: PostgreSQL на тех же дисках, что и файловый сервер, - конкуренция за IOPS.
- Нет резервирования и бэкапов - откат миграции невозможен.

### Данные и хранилища
- Excel и сканы без схемы: долгий ETL, ручная выверка, дубли пациентов.
- Ключ пациента «Ф. И. О. + дата рождения» даёт коллизии при слиянии в `patient_id`.
- Двойной учёт (Excel + 1С) - расхождения, сверка на каждом шаге.
- Пятикратный рост: индексы, партиционирование и retention не спроектированы.
- Шифрование полей и аудит добавляют задержку на каждую операцию с медкартой.
- Конвертация файловых баз 1С - длинные транзакции и блокировки.

### Программное обеспечение
- Распределённые транзакции между доменами (запись -> счёт -> уведомление).
- N+1 и «болтливые» вызовы между сервисами там, где в монолите был один запрос.
- Gateway + OPA + mTLS - дополнительные хопы и проверки на каждом запросе.
- Нет кэширования справочников (расписание, прайс).
- Синхронные HTTP-вызовы 1С блокируют кассу при недоступности.
- Несовместимые изменения контрактов ломают порталы.

### Интеграция
- Партнёрский API лаборатории без SLA - очереди заказов растут.
- Таймауты платёжного провайдера и ОФД блокируют приём оплаты.
- Лимиты и задержки SMS/push-провайдеров.
- Параллельная работа монолита и сервисов - двойная запись и расхождения.
- Федерация AD/Keycloak: сбой входа затрагивает весь персонал.

### Персонал
- ИТ-отдел из 3 человек без DevOps, DBA и ИБ - узкое место на каждом этапе.
- Технический директор совмещает роли архитектора и руководителя - единая точка решений.
- Ресепшен и врачи не обучены порталам - ошибки ввода и обходные пути через Excel.
- Массовый наём: новички без регламентов, рост нагрузки на поддержку.
- Нет on-call и процедур реагирования.

### Процессы
- Миграция «большим взрывом» вместо поэтапной.
- Нет нагрузочного тестирования и SLO до переключения.
- Нет плана отката и критериев go/no-go.
- Ручные релизы без CI/CD и Privacy Gate.
- Запись пациентов продолжается во время миграции - окна простоя не согласованы.
- Нет мониторинга: деградация обнаруживается по жалобам.

## 3. Рекомендации и приоритеты

Приоритет: P1 - без этого миграцию начинать нельзя; P2 - до переключения
первого домена; P3 - до финального состояния.

| № | Мера | Категория | Приоритет | Эффект |

## 4. Главные риски снижения производительности

1. **Параллельная работа старой и новой систем на одном сервере** - самый
   вероятный источник деградации в первые месяцы; закрывается мерами 1-2.
2. **Рост числа сетевых вызовов на один бизнес-сценарий** (шлюз, OPA,
   mTLS, межсервисные вызовы, шифрование) - без кэшей и бюджета задержек
   сценарий «открыть карту» станет заметно медленнее монолита; меры 9-10.
3. **Внешние зависимости в синхронном пути** (лаборатория, PSP, ОФД,
   SMS) - блокируют приём и оплату; мера 8.
4. **Данные без схемы и дубли** - длинный ETL и ручная выверка затягивают
   каждое переключение; мера 5.
5. **Команда из трёх человек** - любая из мер выше упирается в людей;
   мера 4 первична.
