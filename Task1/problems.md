## 4. Проблемные зоны

1. **Нет границы между хранилищем и пользователем.** Все медицинские данные
   лежат на общем диске, доступном любому доменному пользователю, и
   открываются напрямую в Excel/просмотрщике. Любой новый сотрудник на
   первый день получает доступ ко всем медкартам.
2. **Нет аудита.** Невозможно ответить, кто и когда открыл карту пациента,
   скопировал файл или переслал анализы. Утечка не будет обнаружена.
3. **Данные не классифицированы.** Нет различия между контактными данными,
   договором, диагнозом и анализами - значит, нельзя применить разные меры
   защиты и нельзя доказать регулятору выполнение требований.
4. **Дублирование и рассинхронизация.** Пациент заведён в `Patients.xlsx`, в
   журналах врачей, в папке пациента, в реестре анализов, в 1С и в
   Excel кассира. Удалить данные по запросу субъекта невозможно: неизвестно,
   где все копии.
5. **Чувствительные данные в почте.** Результаты анализов и переписка с
   лабораторией и пациентами ходят через Exchange без шифрования и DLP;
   почта - основной канал утечки.
6. **Файловый режим 1С.** База - это файл на общем ресурсе: нет
   разграничения прав внутри базы, нет журнала, любой с доступом к папке
   может скопировать всю бухгалтерию и кадровые данные.
7. **Интеграция ККМ по OLE через TCP/IP** в общей сети без аутентификации и
   шифрования; платёжные данные можно перехватить и подменить.
8. **Один физический сервер в офисе** с AD, DNS, DHCP, файлами, почтой и 1С:
   единая точка отказа и единая точка компрометации; физический доступ к
   нему есть у сотрудников офиса.
9. **Нет процессов data privacy:** нет согласий на специальную категорию
   ПДн, нет сроков хранения, нет уничтожения, нет ответственного за ПДн,
   нет процедуры реагирования на инциденты и уведомления РКН.
10. **Нет Privacy by Design для нового.** Портал, мобильное приложение,
    интеграция с лабораторией и озеро данных проектируются без требований к
    конфиденциальности - риск перенести текущие проблемы в новую систему и
    умножить их на 5 с ростом объёма.

## 5. Что улучшить

- Ввести реестр данных и классификацию (см. Task3), назначить владельцев
  данных и ответственного за ПДн.
- Убрать прямой доступ к файлам: данные пациентов переносятся в сервисы
  с API и RBAC/ABAC, общий диск остаётся только для нечувствительных
  документов.
- Минимизация: собирать расширенную анкету только по показаниям, хранить
  в домене «Медкарта», а не рядом с контактами.
- Разделить домены данных: Identity (контакты, договор), Clinical
  (медкарта, анализы), Billing (платежи), HR/Finance. Между доменами -
  только через API с псевдонимизированным идентификатором пациента.
- Тегирование данных на уровне схем и API-контрактов (см. ниже), на основе
  тегов - автоматический контроль в CI и маскирование в логах/аналитике.
- Аудит всех обращений к тегированным данным с отправкой в SIEM, алерты на
  нетипичное поведение (массовое чтение карт, доступ вне рабочего времени).
- Шифрование: диски и БД at rest, TLS везде in transit, mTLS между
  сервисами, шифрование полей специальной категории на уровне приложения.
- Почта: запрет пересылки медицинских данных, DLP, обмен с лабораторией
  только через API с mTLS.
- 1С перевести в клиент-серверный режим (PostgreSQL), включить журнал
  регистрации, ограничить роли.
- Сегментация сети: ККМ, серверы, рабочие станции, гостевой Wi-Fi - в
  разных VLAN; серверы - в ЦОД или облаке с 152-ФЗ.
- Регламенты: согласия, сроки хранения и уничтожения, процедура запроса
  субъекта, обучение и NDA при найме.

## 7. Механизм тегирования данных

1. **Каталог данных** - OpenMetadata (альтернатива: DataHub). Каждый
   источник (PostgreSQL, S3, ClickHouse, Kafka-топики) подключён к каталогу;
   таблицы, колонки и объекты получают теги из единого словаря:
   `pii:direct`, `pii:contact`, `pii:special`, `medical`, `financial`,
   `hr`, `legal`, `audit`, `public`.
2. **Теги в коде, а не только в каталоге.**
   - В миграциях БД: `COMMENT ON COLUMN patients.birth_date IS 'tag:pii:direct'`
     и расширение `pg_catalog` для автоматической синхронизации в каталог.
   - В API-контрактах: OpenAPI `x-data-tags: [pii:special]` на полях схем.
   - В событиях Kafka: заголовок `data-tags` и теги в Schema Registry.
3. **Автоматическая классификация** - профилировщик каталога (регулярные
   выражения и ML-классификаторы OpenMetadata) находит нетегированные
   колонки, похожие на ПДн, и создаёт задачу владельцу данных.
4. **Контроль в CI/CD** - линтер контрактов: поле с тегом `pii:special`
   не может попасть в публичный API, в лог или в топик без тега; релиз
   блокируется. Результат проверки публикуется в мониторинг.
5. **Применение тегов в рантайме** - политики OPA/Open Policy Agent:
   по тегу поля и роли/атрибутам субъекта принимается решение о доступе,
   маскировании или отказе; логи с тегированными полями проходят через
   маскирующий процессор (Vector/Logstash) до записи.
6. **Data Lineage** - каталог строит происхождение данных от источника до
   витрины и отчёта; при запросе субъекта на удаление по lineage находятся
   все копии.

## 8. Инструменты и меры по потокам

| Поток | Меры |
|---|---|
| Пациент -> ресепшен/портал (анкета, запись) | HTTPS/TLS 1.2+, согласие на обработку, минимальная форма, капча и rate limit, валидация, запись в домен Identity через API |
| Ресепшен -> хранилище пациентов | RBAC: ресепшен видит контакты и расписание, не видит медкарту; аудит в SIEM |
| Врач -> медкарта | ABAC: врач видит карты только своих пациентов (по записи на приём); шифрование полей; аудит каждого открытия |
| Лаборатория <-> клиника | API с mTLS и OAuth2 client credentials, псевдоним пациента вместо Ф. И. О., подписанные ответы, запрет почты |
| Кассир -> платёжный шлюз -> 1С | TLS к ККМ и шлюзу, без хранения PAN, подписанные фискальные документы, единый источник - без Excel |
| Склад/бухгалтерия -> 1С | клиент-серверный режим 1С, роли, журнал регистрации, TDE PostgreSQL |
| Сервисы -> озеро данных/BI | ETL с обезличиванием (псевдонимизация, обобщение дат и адресов), витрины без `pii:direct`, RLS в ClickHouse |
| Все сервисы -> логи и мониторинг | маскирование тегированных полей, централизованный аудит, алерты на аномалии |
| Резервное копирование | шифрование, хранение в РФ, тест восстановления, срок хранения по политике |
| Рабочие станции | шифрование дисков, запрет USB, DLP, запрет локального хранения медданных, MFA в домене |
